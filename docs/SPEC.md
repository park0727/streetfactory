# Streetfactory ERP/WMS — 확정 스펙

오토바이 수리·부품 업체 Streetfactory 의 해외 수입 부품 재고·판매·거래처 관리 시스템.
Google 스프레드시트로 운영하던 업무를 웹 앱으로 옮긴다. 기존 데이터 이관은 없다.

## 1. 규모와 전제

- 사용자 2~3명, 내부 직원 전용. 동시 접속 10명 미만.
- 부품 수천 개, 거래 연 수천~수만 건.
- 운영비 0원 목표. 모든 인프라는 무료 티어 안에서 동작해야 한다.

## 2. 인프라

| 영역 | 선택 | 비고 |
|---|---|---|
| 호스팅 | Cloudflare Workers (OpenNext 어댑터) | 하루 10만 요청, 요청당 CPU 10ms. 상업 이용 허용 |
| DB / 인증 | Supabase 무료 티어, 서울 리전 | Postgres 500MB, Auth 포함 |
| DB 접속 | postgres.js + Drizzle, Supavisor 트랜잭션 풀러(6543) | Workers 에서 TCP 연결. `prepare: false` |
| 프레임워크 | Next.js 16 App Router, TypeScript | Server Actions 로 폼 처리 |
| UI | Tailwind v4 + shadcn/ui, TanStack Table, Recharts | 네이비/슬레이트 B2B 테마 |
| 엑셀 | exceljs, **브라우저에서** 생성·파싱 | Workers CPU 제한 회피. 서버는 JSON 만 처리 |

### CPU 10ms 제한 대응 원칙
- 엑셀 생성/파싱은 클라이언트에서 한다.
- 대량 조회는 페이징한다. 대시보드 집계는 SQL 에서 끝내고 앱 서버는 결과만 전달한다.
- 무거운 계산은 DB 함수/뷰로 내린다.

## 3. 사용자와 권한

- 역할 두 가지: `admin`, `staff`.
- admin 은 사용자 생성·비활성화·비밀번호 초기화를 한다. staff 는 자기 비밀번호만 바꾼다.
- 계정마다 모듈 접근 플래그: `can_parts`(부품·재고·판매·거래처), `can_repair`(정비, 2차).
- 사용자 생성은 초대 메일 없이 admin 이 이메일 + 임시 비밀번호로 직접 만든다
  (Supabase 기본 SMTP 는 발송 제한이 커서 메일 의존을 없앤다). 첫 로그인 시 비밀번호 변경을 강제한다.
- 로그인 방식: 이메일 + 비밀번호 (Supabase Auth). 회원가입 화면은 없다.

## 4. 핵심 비즈니스 규칙

### 4.1 기준정보(SSOT) 와 거래 스냅샷 분리
- 부품 마스터가 부품명·카테고리·호환기종·제조사·표준원가·권장소비자가의 유일한 원천이다.
- 판매 라인은 `unit_price`(적용단가), `unit_cost`(적용원가) 를 거래 시점 값으로 **복사 저장**한다. 마스터가 바뀌어도 과거 원장은 불변.
- 입고 라인은 외화단가·환율·원화단가·배분 부대비용·개당 실질원가를 모두 저장한다.

### 4.2 원가 기준: 이동평균 원가
- 부품마다 `avg_cost` 를 유지한다.
- 입고 확정 시: `avg = (현재수량 × avg + 입고수량 × 개당실질원가) / (현재수량 + 입고수량)`. 현재수량 ≤ 0 이면 `avg = 개당실질원가`.
- 기초재고 등록 시 단가를 받아 초기 avg 로 쓴다.
- 판매 라인의 `unit_cost` 는 판매 시점의 `avg_cost` 스냅샷. 매출이익 = `qty × (unit_price − unit_cost)`.
- 재고평가액 = `현재재고 × avg_cost`. 마스터의 `standard_cost` 는 참고값이자 입고 이력 없는 품목의 avg 초기값.
- 개당 실질원가 = `(수량 × 원화단가 + 라인 배분 부대비용) / 수량`. 부대비용(관세 + 기타) 은 전표 단위 입력, 라인 **수량 비례** 배분.

### 4.3 재고
- 재고는 `stock_movements` 한 테이블에만 기록한다. 유형: `opening`(기초), `inbound`(입고), `sale`(판매), `adjustment`(실사조정).
- 현재재고 = `SUM(qty)` (부호 포함). 별도 재고 컬럼을 두지 않는다.
- 재고상태 판정: 현재재고 ≤ 0 → `품절`, 0 < 현재재고 < 안전재고 → `안전재고 부족`, 그 외 `정상`.
- 판매 등록 시 현재재고 초과면 경고를 띄우되, 저장은 admin 만 강제 진행 가능 (음수 재고 허용 여부는 설정으로).

### 4.4 부품코드 불변
- `parts.code` 는 생성 후 수정 불가. 단종은 `status = discontinued` 로 처리. 삭제 없음.
- 운영상태(`active / paused / discontinued`) 는 수동 플래그. 재고상태와 별개.

### 4.5 전표 채번
- 판매 `SLS-YYYY-NNNNN`, 입고 `INB-YYYY-NNNNN`, 거래처 `P-NNNN`. 5자리, 연도별 리셋.
- `doc_sequences` 테이블을 `UPDATE … RETURNING` 으로 잠가 동시 입력에도 중복이 없게 한다.

### 4.6 금액과 세금
- 모든 저장 금액은 **공급가액(부가세 별도)**. 화면과 엑셀에는 부가세 포함가를 함께 표시.
- 원화는 소수점 없이 정수 원. 외화 단가는 소수 4자리. 환율은 소수 4자리.

## 5. 엑셀 일괄 업로드

대상: (1) 부품 마스터 신규/수정, (2) 수입 입고전표.

흐름: 템플릿 다운로드 → 파일 선택 → 브라우저에서 파싱 → 검증 결과 표(오류 행 강조) → 확정 → 서버에 JSON 전송 → 단일 트랜잭션 저장.
- 오류가 1건이라도 있으면 전체 저장하지 않는다.
- 부품 마스터 업로드: `code` 가 있으면 수정, 없으면 신규. `code` 자체는 바꿀 수 없다.
- 입고 업로드: 파일 1개 = 전표 1건. 전표 헤더 항목(입고일, 공급사, 통화, 환율, 관세, 부대비용, 운송방식) 은 업로드 화면에서 입력.

## 6. 모바일

- 전 화면 반응형. 표는 가로 스크롤 허용.
- 입출고 간편 등록은 모바일에서 판매/입고 탭 전환 레이아웃. 부품 검색은 큰 입력창 + 최근 사용 품목.
- 바코드 스캔은 제외. 부품 검색창은 코드 정확 일치 시 즉시 선택되게 만들어 나중에 스캐너 입력과 호환.

## 7. 범위

### 1차 (이번)
대시보드, 부품 마스터, 재고, 입출고 간편 등록, 거래처, 거래처 원장, 판매/입고 원장, 엑셀 다운로드/업로드, 사용자 관리.

### 2차 (별도 정리)
정비 모듈: 접수, 차량 정보, 공임, 사용 부품(판매 원장·재고와 연결), 정산. 스키마에 `sales_orders.source = 'repair'` 와 `repair_order_id` 자리를 미리 둔다.
